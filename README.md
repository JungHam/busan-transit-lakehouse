# busan-transit-lakehouse

부산 시내버스 실시간 위치 데이터(국토교통부 TAGO 공공 API)를 수집·정제·적재하는 데이터 파이프라인 프로젝트입니다.

> **상태: 계획 단계** (2026-10-12 ~ 2027-01-10, 90일). 아래 구성은 목표이며 아직 구현되지 않았습니다. 진행에 따라 이 문서를 갱신합니다.

## 왜 만드나

공간정보 데이터를 오래 다뤘지만 처리는 스케줄러에 거는 스크립트 배치가 전부였고, 재실행과 중복 처리는 수작업으로 해결했습니다. 누구나 접근할 수 있는 공공 API로도 이런 데이터를 재시도·멱등성·재처리가 갖춰진 구조로 자동화할 수 있음을 보이는 것이 목표입니다.

버스 위치 데이터는 계속 쌓이고, API 장애·지연·빈 응답이 일상이며, 위치라는 공간 속성이 있어 이 목적에 맞습니다. 대상 지역은 서울 버스 API 문제로 TAGO(`cityCode=21`)의 부산을 택했습니다.

## 구성 요소

| 구성 | 상태 | 링크 |
|---|---|---|
| 수집 모듈 (TAGO 호출, 재시도, 시간 파티션 raw 적재) | 구현됨 | [bus_location_data_processing](https://github.com/JungHam/bus_location_data_processing) |
| 오케스트레이션 (Airflow) | 계획 | - |
| 정제 (Spark / DuckDB 규모별 비교) | 계획 | - |
| 레이크하우스 테이블 (Iceberg) | 계획 | - |
| 마트 모델링 (dbt) | 계획 | - |
| 클라우드 배포 (AWS) | 계획 | - |

## 계획 중인 마트

- 시간대 × 노선 운행 밀도
- 정류소별 시간대 통과 차량 수
- 기상 조인 운행 패턴

## 설계 원칙

- 장애가 나도 스스로 복구된다 (재시도·백오프)
- 재실행해도 중복이 없다 (멱등 키)
- 과거를 다시 계산할 수 있다 (backfill)
- 품질이 검증된다

주요 결정은 ADR로 기록할 예정입니다 (멱등 키, catchup, 정제 엔진 비교, 카탈로그, small files, dbt 엔진, 품질 게이트, 관리형 vs 자가 운영).

## 알려진 제약

TAGO 응답에 측위 시각 필드가 없어, 관측 시각은 수집 배치의 논리 시각(`dt=/hour=`)으로 근사합니다.
